# Comparison-analysis JSON · format v1

Use **Export comparison** on Compare. Use **Export dataset** on Data & portability for the canonical raw telemetry backup. They are separate artifacts with different purposes. Analysis exports are not importable telemetry and the importer explicitly rejects them.

PennyTel 0.2.0 exports raw telemetry as schema v2 and reports `source.datasetSchemaVersion: 2` here. The analysis format remains version 1. Structured execution evidence is retained in raw exports; it does not introduce new derived metrics, infer workflow labels, or feed quota readings into the existing usage-burn analysis.

The renderer sends only `{ revision, context }` through the typed preload API. The main process validates the request, reads its own authoritative dataset, rejects a stale revision, and builds analysis using `src/shared/comparison.ts`, also used by the UI. It never trusts derived metrics supplied by the renderer. Native save dialogs and the live-file/backup protection are shared with raw export. Export is read-only with respect to the dataset and its revision. App version comes from bundled package metadata, including when launching the built Electron entry file directly.

| Field                   | Meaning                                                                                                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`                  | `pennytel-comparison`                                                                                                                                                                       |
| `analysisFormatVersion` | `1`; distinct from dataset schema version                                                                                                                                                   |
| `app`                   | PennyTel name and actual running app version                                                                                                                                                |
| `source`                | Raw dataset schema version and revision at export                                                                                                                                           |
| `generatedAt`           | ISO timestamp with timezone                                                                                                                                                                 |
| `context`               | Active filters, `groupBy`, sort (`label`, `cost`, `time`), optional selected group, selected Model Configuration keys, and stage scopes                                                     |
| `cohort`                | Eligible slice IDs, qualified slice IDs, matching run IDs, displayed evidence run IDs, resolved selected group                                                                              |
| `summary`               | Overall matching-run metrics, recorded defect counts, validated autonomous discoveries, accepted-slice quality distribution                                                                 |
| `groups`                | Ordered groups, membership IDs, run metrics, findings/discovery IDs and counts, distinct accepted-slice grade distributions                                                                 |
| `candidates`            | Selected configuration keys/labels in selection order, scoped membership, coverage-aware metrics, linked evidence, and touched-slice dispositions                                           |
| `acceptedSlices`        | Qualified accepted slices with all relevant lifecycle run IDs, outcome judgment, elapsed acceptance time/basis, role cost, severity/category evidence, discoveries, and timing completeness |
| `conventions`           | Interpretation of tokens, meter, cohort, acceptance, evidence attribution, quality, and unknown values                                                                                      |

Context filters use the same keys as the UI: project, taskShape, ambiguity, risk, productionModel, experiment, disposition, qualityGrade, modelConfiguration, canonicalModel, modelFamily, model, thinking, role, sessionMode, contextMode. Cleared filters are omitted. Grouping supports modelConfiguration (the default), canonicalModel, modelFamily, model, thinking, role, slice, candidate, productionModel, sessionMode, contextMode, localHour, dayOfWeek. A selected group only narrows the underlying-evidence list, as in the UI; it does not change the comparison cohort or acceptance costs.

Slice 3 adds optional `context.selectedCandidates` and `context.stageScopes`. Omitted collections mean empty selection, preserving older analysis-v1 requests. This state is ephemeral: it travels with the analysis request/export and is not written into telemetry or restored on app restart. Keep the context and the matching raw dataset revision to reproduce the workspace through `compareData()`.

- `selectedCandidates` contains up to **8 unique canonical Model Configuration keys**, in column/selection order. Eight is an explicit small-workspace limit; larger datasets remain accessible through the existing groups and filters. Each key must be a canonical JSON configuration tuple with a valid model-identity tuple and recorded thinking vocabulary, within `MAX_DERIVED_IDENTITY_LENGTH` and the existing source-string limits. Presentation labels and `XHigh` are not key values.
- Candidate selection is separate from ordinary filters and `selectedGroup`. Selected keys match alternative candidates (OR); each candidate partitions the already-qualified observed runs. Selection does not remove runs/slices from the base cohort or assign accepted economics to candidates. A candidate with no scoped runs stays present, with count 0 and unknown cost/time/token totals.
- `stageScopes` contains up to **16 unique scopes**. `{ "kind": "role", "value": "Implementer" }` is Implementation; `Critic` and `Repair` match their exact structured roles. `{ "kind": "runType", "value": "Verification" }` matches that exact recorded source text. Scope objects have exactly those two fields; run-type text is nonblank and bounded to 100,000 UTF-16 units. Duplicates are rejected regardless of object property order.
- The UI offers exact run types present in the dataset, preserving case and whitespace. Re-critic/Verification have no inferred role mapping or built-in normalized stage. Unknown or unavailable stage identity is never assigned from chronology, result, tests, findings, or links.
- Multiple stage scopes OR together, then AND with all ordinary run-filter conditions on the same run. Active stages qualify only slices containing scoped matching evidence. No stage selection preserves all-run behavior, including eligible empty slices. Qualified accepted slices still retain their full relevant lifecycle across stages and candidates.

The additive top-level `candidates` array follows selected-key order. Every entry includes `key`, dataset-wide collision-safe `label`, `runIds`, `sliceIds`, `metrics`, linked `findings`, `defects`, linked `discoveries`, and `sliceDispositions`. Candidate discoveries include all linked records, with their recorded validation status; the existing group/summary validated-autonomous counts retain their established stricter predicates. Dispositions count distinct touched slices and do not attribute the slice outcome to the candidate. Run IDs resolve to inspectable source records in the matching raw export. The existing `groups`, `cohort.evidenceRunIds`, and `selectedGroup` keep their presentation semantics independently of candidate columns.

Model Configuration is derived by `src/shared/configuration.ts`: a valid recorded registry model ID wins; otherwise the existing registry resolver must resolve canonical/API/alias names with provider evidence unambiguously. Unresolved identity keeps the exact recorded model text and any explicit unresolved model ID. No new alias matching is introduced. Provider and offer are not configuration dimensions, and pricing resolution is unchanged.

The canonical model key is the JSON tuple `["model", modelId]`; unresolved model keys are `["unresolved-model", modelId-or-null, exact-model-or-null]`. Configuration keys are JSON tuples `[model-key-string, recorded-thinking-or-null]`. Missing thinking is a distinct null key component displayed as **Unknown**; it is never inferred from capabilities. Recorded `ExtraHigh` displays as **ExtraHigh / XHigh**, but the key and raw telemetry retain `ExtraHigh`. This does not add `XHigh` or registry `xhigh` to the telemetry import vocabulary. Display labels are not identities: filters and selected groups use the keys, so equal labels cannot merge different IDs.

`canonicalModel` rolls configurations together by that same model identity. `modelFamily` groups exact recorded family evidence with keys `["family", family-or-null]`; missing family remains Unknown. Existing `model` (Exact model) and `thinking` dimensions retain their source-field semantics. None of these derivations persists new fields, migrates data, changes snapshots, or recalculates historical prices. The format remains additive analysis v1; raw telemetry uses schema v2.

Each metric bundle reports run count, cost in USD, mean cost of priced runs, summed wall-clock minutes, usage burn in percentage points, weighted cache ratio/coverage, repair pass count, and role cost totals. Numeric measurements are not display-rounded.

Each bundle also includes `evidence.numeric` measured totals for `inputTokens` (fresh), `cachedInputTokens`, `outputTokens`, `reasoningTokens`, `filesChanged`, `testsAdded`, `testsPassed`, `testsFailed`, and `testsSkipped`. Reasoning remains a subset of output and never enters pricing independently. File and test totals sum recorded run counts; they do not assert unique files or tests across runs. `evidence.buildResult`, `runtimeTested`, `result`, and `role` report `{ counts: [{ value, count }], recorded, total, complete }`. Missing booleans are unknown; recorded `false` remains No. Candidate `sliceDispositions` uses the same count shape with a distinct-slice denominator.

Cost means cover priced runs only, with the denominator in `costUSD.recorded`. Cache coverage counts runs with both input counts; even complete input-pair coverage can yield a null ratio when the summed denominator is zero. Burn uses existing reset/increase/explicit-override semantics and includes coverage. There is no weekly usage series for the operator remaining-percentage meter; v2 coarse source quota windows do not supply one. File lists, test names, and verification artifacts are likewise unavailable and are not synthesized.

Totals use:

```json
{
  "knownTotal": 6,
  "completeTotal": null,
  "recorded": 3,
  "total": 4,
  "complete": false
}
```

This means 3 of 4 relevant runs have that measurement and sum to 6; the complete total is unknown. A wholly unknown measurement has `knownTotal: null`. Known zero is `0`. A role with no recorded runs has a zero subtotal; a role with recorded but wholly unpriced work has an unknown subtotal. Empty comparison/run sets are not represented as known free work. Ratio denominators of zero are unknown. Empty role subtotals do not assert there was no unrecorded work.

Defects preserve separate `bySeverity`, `byCategory`, and `bySeverityAndCategory` counts. Dismissed findings and observations are counted separately and excluded from defects. These are counts of recorded evidence; zero does not prove defect-free work. Run/group finding counts attribute where findings were discovered, not fault. Accepted-slice counts retain all slice evidence, including later evaluation.

Quality remains operator judgment on the integer 1–5 scale. Distributions include graded/ungraded counts and counts for each grade. A group’s quality distribution concerns distinct accepted slices touched by its matching runs; it does not assign the whole outcome to a single model. No synthetic weighted score is created.

Acceptance economics qualify slices using all active filters and stage scopes, then include their full relevant lifecycle through acceptance, including other models' critics, repairs, and overhead. Candidate selection does not affect qualification or lifecycle cost. Undated runs remain included and listed. Missing acceptance timestamps are flagged as unbounded. Known costs can be complete for recorded runs even when acceptance timing is incomplete; those two coverage dimensions are kept separate.

PennyTel 0.1.3 introduced `acceptedSlices[].outcome` through the existing shared comparison derivation, with raw schema and analysis format version 1 at that time. The outcome semantics remain the same with raw schema v2. Each accepted slice is one sample (`sampleCount: 1`); the number of accepted outcomes is the length of `acceptedSlices`, not the number of runs or model configurations. The accepted slice's existing `costUSD`, `wallMinutes`, and `evidence.numeric` fields describe its full recorded lifecycle. Wall minutes sum run durations, including overlapping work; `timeToAcceptedMinutes` is separately measured elapsed time or the interval from the earliest recorded start. An explicit slice time takes precedence, including zero. Incomplete timestamps remain visible even when cost or wall-duration coverage is complete.

The outcome object contains:

- `stages`: exact `(role, runType)` groups, each with source `runIds` and the existing metric bundle. Free-text Re-critic, Verification, and support-stage names are preserved without normalizing them into new roles. The list contains recorded stages only; an absent stage is not evidence of zero work.
- `acceptanceWindow`: the same bounded/undated/complete-timing metadata exposed on the accepted slice. `evidenceGaps` identifies absent lifecycle runs, implementation, explicit run acceptance, results, or timing. These describe recorded evidence, not proof that every real-world stage was captured; the telemetry schema has no lifecycle-capture assertion.
- `firstPassAcceptance`: `state` (`Yes`, `No`, or `Unknown`), explanatory `basis`, and supporting run/finding IDs. `No` requires Repair-role work, an explicit repair link, a `Needs repair` run result, or a non-dismissed finding recording repair required/performed. `Yes` requires exactly one implementation explicitly marked `Accepted`, a bounded acceptance window, dates and successful results on all recorded lifecycle runs, and no conflicting repair or unresolved defect evidence. Missing price/token/runtime measurements do not override direct acceptance evidence; their own coverage remains incomplete. Merely recording a slice as Accepted, or an implementation as Completed followed by an accepting review, does not establish first-pass success. Such cases remain Unknown. Multiple implementations without explicit repair evidence also remain Unknown.
- `repair`: unique recorded repair-run count/IDs, required-run and finding IDs, measured repair cost, and the repair/implementation cost ratio. Repair runs are the union of structured Repair-role runs and explicitly linked repair runs within this lifecycle, even if a linked run has another role. Duplicate finding links never double count cost. No recorded repair runs means unknown repair economics unless direct first-pass evidence establishes zero. A zero or unknown implementation-cost denominator, missing linked repair work, or unpriced repair/implementation work leaves the ratio null. Counts are recorded runs, not inferred repair cycles or a guarantee that no other repair work occurred. The legacy `repairPasses` and `roles.Repair` fields retain their structured-role meanings; use `outcome.repair` for explicit repair-link evidence.
- `reasoningShare`: reasoning/output ratio over runs with both counts, with `knownRuns`, `totalRuns`, and `complete` paired coverage. The ratio is null for a zero denominator; partial ratios describe the paired subset. Reasoning remains within output and is never charged independently.

`evidence.runtimeTested` and stage runtime counts report the recorded Yes/No values and missing coverage. They do not invent an operator QA verdict, infer a passing result, or convert missing telemetry to No. Source runs remain inspectable in the UI. Findings linked only to dated post-acceptance runs do not rewrite first-pass status; all slice findings remain in the existing defect evidence. Unlinked findings lack timestamps and remain potentially relevant, conservatively preventing unsupported first-pass claims.

The Compare workspace displays a per-outcome summary and expandable lifecycle stages, token totals, reasoning share, and source runs. Its deterministic and Electron QA use `tests/accepted-outcome-fixture.json`: synthetic identities and frozen test prices with production-shaped Codex token counts, including a six-stage Astra/Luna repair lifecycle, direct acceptance, incomplete telemetry, known zero, and an empty accepted slice. It is test data, never a bundled production dataset or an operator profile.

Retain the matching raw dataset export to inspect source evidence and saved pricing. A revision is local to one dataset, not a globally unique experiment ID. Prices are not fetched or recalculated from current market rates during export.

## PennyTel 0.1.4 analytics and filters (additive analysis v1)

The dataset schema, persistence authority, immutable saved prices, and non-importable analysis discriminator are unchanged. `src/shared/analytics.ts` owns descriptive run statistics, reasoning share, cost composition, and temporal inputs. `compareData()` derives these plus accepted aggregates for both Compare and main-process export. The workspace uses native React/CSS/SVG visuals, with no additional chart dependency.

Additional ordinary filter/group dimensions are `provider` (exact recorded text), `providerId` (exact recorded ID), `offerId` (saved `priceSnapshot.offerId`), `runType` (exact recorded stage), `runtimeTested` (`"true"` or `"false"`), and `result` (recorded run result). Provider identity is not silently resolved from another field, and saved offer identity is not inferred from the current registry. Grouping additionally supports `project`, `ambiguity`, `risk`, `disposition`, and `qualityGrade`. New recorded-field groups use JSON keys `["recorded", value-or-null]` to distinguish missing evidence from literal text `Unknown`. Existing group keys retain their prior meaning.

Ordinary filters now allow **null** to select missing evidence explicitly. Omitted or empty-string filters remain cleared; the literal strings `Unknown`, `false`, and `0` retain exact recorded meanings. For derived Model Configuration/canonical-model filters, null selects runs with neither model text nor model ID; unresolved but recorded identities remain evidence. Model-family null selects missing recorded family. Configuration keys still encode missing thinking explicitly. Filter combinations are AND, with all run-backed conditions required on the same run. Selected stage scopes retain their existing OR semantics.

The current telemetry schema has no dedicated technical-stack tags, difficulty/coupling scores, evidence class, or explicit context-preparation state. The UI identifies those absences; no filter values or evidence are synthesized from notes, task shape, context mode, or role names. Runtime-tested state is recorded boolean evidence, not a separate operator QA verdict. Project is the recorded product/project field; slice disposition remains the accepted-state filter.

Optional `context.dateRange` has `{ from?, to?, includeUnknown }`. At least one bound is required. Bounds are canonical UTC ISO timestamps (`YYYY-MM-DDTHH:mm:ss.sssZ`), inclusive, valid dates, and ordered. `includeUnknown` is a required boolean when a range is present. The UI supplies the beginning/end of the selected UTC days; requests may specify precise instants. A missing run start qualifies a date range only when explicitly included. The range applies to `Run.startAt`, not the slice date, acceptance date, or inferred chronology. Empty slices cannot qualify an active run/date condition.

Optional `context.outcomeFilters` contains any of:

- `firstPass`: `Yes`, `No`, `Unknown`, using the established accepted-outcome evidence.
- `repairPresence`: `Yes` when repair work or a requirement is explicitly recorded; `No` only when first-pass acceptance is established; otherwise `Unknown`.
- `repairBurden`: `Zero`, `Positive`, `Unknown`, describing recorded repair cost. Zero/positive requires complete repair pricing plus no unresolved repair links or required-but-missing work. Zero recorded repair rows alone remains Unknown. This is a cost category, not an inferred repair-cycle count or confidence judgment.

Any active outcome filter restricts the **whole cohort** to accepted slices meeting that full-lifecycle predicate. Ordinary run filters/date ranges/stage scopes then qualify runs within those slices. Accepted metrics always reopen each qualifying slice's complete relevant lifecycle, including other models and stages and undated work. Changing filters does not edit telemetry. These objects are bounded and whitelisted by `validateComparisonRequest()`; the main process still rejects stale revisions or renderer-supplied derived data. Clearing filters resets ordinary, date, and outcome filters, preserving separately controlled candidate and stage selections.

New top-level exported inputs:

| Field               | Meaning                                                                                                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `analytics`         | Current observed cohort's run statistics, composition, reasoning share, and source `runIds`                                                                                                          |
| `temporal`          | UTC-day trend inputs, undated run IDs, and individual time/cost inputs                                                                                                                               |
| `acceptedAnalytics` | One sample per qualified accepted slice, with full-lifecycle source IDs, aggregate statistics, stage totals, first-pass distribution, repair burden, quality summaries, and per-outcome chart inputs |

Every existing metric bundle also gains `analytics`, including groups, selected candidates, accepted slices, and lifecycle stages. Run analytics contain `sampleCount`, `runIds`, cost and wall-time distributions, `costComposition`, and coverage-aware `reasoningShare`. Distributions expose `sampleCount`, `knownCount`, `unknownCount`, `mean`, `median`, `min`, `max`, and `sampleStandardDeviation`. Math uses unrounded recorded values. Sample SD uses the n−1 denominator and is null below two known samples; min/max describe the observed range. Empty/all-unknown means and medians remain null; recorded zero participates normally. These are descriptive summaries, not confidence intervals or estimates for missing samples.

`costComposition` contains measured `freshInputUSD`, `cachedInputUSD`, and `outputUSD`. All three use the same fully priced run subset as `runCost()`, so their sum reconciles to known run cost. Partially unpriced runs do not contribute disconnected components. Each component carries the priced-run denominator and incomplete indicator. Reasoning never contributes a fourth billed component.

`temporal.days` is ordered by the UTC calendar day of actual recorded run starts. Each day contains run analytics and IDs. Missing calendar days are not inserted as zero observations. `undatedRunIds` explicitly lists excluded temporal evidence. The UI flags fewer than two recorded days as insufficient to establish a temporal trend. `timeCost` retains every scoped run with run/slice IDs, recorded start or null, cost or null, and wall time or null. The scatter plot includes only paired known values and displays omitted-sample counts; point actions open source records.

`acceptedAnalytics.costUSD` and `.wallMinutes` summarize **complete recorded per-outcome totals**, not partial subtotals. Their denominator is accepted slices. `knownLifecycleCostUSD` separately sums available lifecycle-run costs with run coverage, so partial work remains visible; it does not claim empty/missing outcomes were free. The UI displays both run coverage and the count of complete outcome costs. Coverage describes captured evidence, not proof that every real-world stage was recorded.

`acceptedAnalytics.firstPass` exposes yes/no/unknown counts, determinable count, and `rate = yes / (yes + no)` or null for no determinable outcomes. Unknown outcomes remain visible beside that denominator. `.repair` contains the recorded repair-run count, complete repair-cost distribution per outcome, and repair/implementation ratio distribution. `.quality` is the distinct accepted-slice operator-grade distribution with graded/ungraded counts. No combined quality or model ranking score is introduced.

`acceptedAnalytics.stages` groups exact role/runType pairs across accepted lifecycles, with source IDs and measured cost/wall totals. `.outcomes` supplies slice identity/title, lifecycle IDs, acceptance timestamp, measured implementation/accepted costs and wall time, grade, first-pass state, and complete repair cost or null. Implementation bars exclude explicit linked repairs even when their recorded role is Implementer. Implementation and accepted bars share a scale and label incomplete known subtotals. Quality/cost plots use only recorded grades and complete recorded accepted costs; they describe whole outcomes, not attribution to one configuration. Details and source IDs preserve inspection of omitted/partial evidence.

Automated analytics coverage is in `tests/analytics.test.ts` and `tests/analytics-ui.test.tsx`; the existing accepted-outcome Electron QA exercises the new workspace using the same isolated production-shaped fixture, including filtering, charts, export, source inspection, narrow layout, and raw-data/restart stability.
